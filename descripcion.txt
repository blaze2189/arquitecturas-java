La arquitectura para este sistema consiste en:
- una aplicaciòn web y app mobile
- cinco microservicios 
- 4 bases de dados relacionales, para mantener consistencia en el manejo de data
- Sistema de cache Redis
- Kafka para la comunicaciòn asínccrona
- Un servidor de arcchivos (S3)
- Un servidor de correos
- Keycloak para la autenticaciòn y autorizaciòn
- un apigateway
- aprovechando la capacidad de la nube se utilizara un VPC para controlar el acceso a los servicios
- Firewall y DDoS para evitar accesos que puedan dañar el funcionamiento del sistema
- se utilizarà kibana para realilzar el trackeo de logs


Flujo de autenticaciòn

- El usuario ingresa su contraseña y password
- Gateway redirecciona llal informaciòn al keycloak para que haga la validaciòn
- en caso de que todo sea correcto se reenvìa el hashcode hata la UI donde serà almacenada en una cookie segura
- en cada request se enviarà ese token para validar la autorizaciòn del usuario

Flujo de Bùsqeuda

- Cada evento que el usuario requira consultar:
 el servicico buscarà primero la informaciòn en la cache, en caso de no encontrarla  

 Flujos de reserva

 - El usuario debe estar logeado, el gateway solicitarà al microservicios de reserva para que inicie el proceso de reserva,
 primero buscarà en cache la disponibilidad de los asientos en caso de exisitir disponibilidad se modificarà el estatus a AWAITING, con la finalidad
 de bloquearlos. Una vez que los asientos han sido bloqueado se envìa la peticiòn al al servicio de pagos para que se comunique cocn el vendor de pagos
 y se guarde la informaciòn de la transacciòn en la bd, cuando todo ha funccionado ccorrectamente el servicio de pagos actualiza la informaciòn del 
 registro en la bd a success, y confirma cocn el servicio de booking para que se actualilce el estado de los asientos a Unavailable, primero en la cache 
 luego en la bd, al final de la transacciòn se enviarà un un mesnaje al microservcico de nortificaciones (mediante colas) parra que envìe un correo de 
 confirmacion al usuario.

 Ccabe menccionar que para encolar la peticiones se aplicara un FIFO, Serviccio de booking reccibirà la peticiòn del request por el usuario, pero el mismo 
 servicio colocara un mensaje en una cola misa que serà consumida por el mismo servicco para iniciar el proceso, este flujo serà asìnccrono, por lo que 
 se utilizara un Serverr Side Event, donde la UI mandtendrà un canal de comunicaciòn abierto con los el gateway para recibir la confirmaciòn (positiva o negativa)
 de la transacciòn.

 Existen dos posibles escenarios de falla, 
 Primero que el asiento ya haya sido reservado por otro usuario, en ese momento el proceso se cancela y se envìa un mesnaje en la UI para el usuario, para que sea
 notificado del porque la transacciòn fue cancelada, en este escenario no se necistarà hacer un rollback en secuencica de las transacccioness.
 Segundo cuando haya fallaldo el pago, iguallmente se enviarà una notificccaciòn al usuario de que la transacciòn fallo, para hacer el rollback,
 el microservicio de payment maracara la transacciòn cocmo Fallida en la bd de pagos, responderà al servicio de reservas para que liberè el asiento dentro de la informaciòn
 en la cache

 Flujo de bùsqueda

  Cada que el usuario quiera buscar informaciòn relacionada a algùn evento, como ubicaciòn, fecha, disponibilidad, el servicio harà la busqueda dentro de los registros de cache,
  en caso de no encontrar informaciòn se irà a la bd a validar la informaciòn

Capa de Dominio (Domain): Representa el núcleo del sistema y contiene el Lenguaje Ubicuo del negocio, las Entidades, Agregados, Objetos de Valor (Value Objects) y las reglas de negocio puras (por ejemplo, la validación de estados del asiento y políticas de reserva). Esta capa es agnóstica a la tecnología y frameworks.

Capa de Aplicación (Application): Contiene la orquestación de los Casos de Uso del sistema (como CrearReserva, ProcesarPago o ConsultarEventos). Se encarga de coordinar el flujo de datos desde y hacia el Dominio, definiendo además las interfaces (Puertos) para comunicarse con componentes externos sin acoplarse a ellos.

Capa de Infraestructura (Infrastructure): Contiene los Adaptadores tecnológicos que permiten la interacción con el mundo exterior. Aquí se implementan los puntos de entrada (Inbound: controladores REST, consumidores de eventos Kafka) y los puntos de salida (Outbound: repositorios de base de datos relacional, cachés en Redis, conectores gRPC/HTTP y productores de mensajería)."
